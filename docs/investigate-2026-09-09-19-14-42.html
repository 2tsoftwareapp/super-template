03

System Overview

Super Template is a production-oriented full-stack monorepo starter for multi-tenant SaaS products. It serves template-consuming development teams and is maintained as a reusable platform rather than a single end-user product.

The system is split into a NestJS API modular monolith, a Next.js admin console behind a cookie/CSRF BFF, a Next.js marketing web app, and a Flutter mobile client. Backend capabilities are packaged as feature modules for identity, organizations, access control, MFA, SSO, users, mail, jobs, files/uploads, imports/exports, notifications, settings, audit, and health. PostgreSQL RLS is the tenant-isolation boundary; Redis is optional in code but intended for shared production throttling/cache behavior.

The main QA concern is not basic compilation. It is whether the verification path proves consumer behavior across the four surfaces and whether production-only distributed behavior is enforced before deployment.

08

Authentication & Permissions

  • Access and refresh tokens are transported through HttpOnly cookies owned by the Next BFF. Mutation routes enforce origin/CSRF guards; deployed environments require secure cookies and CSRF secrets.
  • The API uses JWT/session guards, ordered authorization guards, role/permission checks, MFA, SSO state/PKCE, and PostgreSQL RLS through a restricted application role.
  • Admin UI access is a client-side resource gate layered over server-side API authorization. This is useful for UX, but it must not substitute for API enforcement; API E2E currently validates the latter more strongly than the UI.
  • Production parity is incomplete for distributed behavior: missing Redis is surfaced as a warning, and the API E2E harness overrides the global throttling guard.

09

API & Network Observations

  • The Nest API exposes 25 controller files behind the configurable global prefix, defaulting to /api/v1. OpenAPI is generated from the composed API and used for TypeScript and Dart clients.
  • Admin and web BFFs keep browser traffic same-origin, proxy backend requests, refresh sessions, and sanitize token envelopes. Admin also exposes notification SSE.
  • Storage supports local filesystem and S3-compatible drivers; file access uses signed URLs and a tracking/cleanup layer.
  • Observed checks: pnpm run generate:check, pnpm run schema:check, repo build, API unit/E2E, mobile tests/analyze/format, and web Playwright. All pass except the two browser assertion failures described in G-03.

Unknowns & Blockers

Known: this review is against the current dirty checkout; no unrelated working-tree change was classified as a confirmed product regression unless a command reproduced it. The repo build, typecheck, unit tests, policy/lint, schema check, generated check, API E2E, mobile format/analyze/test all pass under the local environment.

Known: CI explicitly excludes health.e2e because of a documented hang risk in .github/workflows/ci.yml:293-295. This is a coverage gap, but its production impact cannot be ranked above the ten findings without reproducing the hang in CI-equivalent infrastructure.

Assumption: “top 10 gaps” means repo-wide QA readiness. If the intended scope is only the active admin layout work, G-01 through G-04 should be re-ranked above the platform/mobile findings.

Unknown: no staging/production URL or real S3, Redis, IdP, mail, or mobile device was supplied. Provider compatibility, deployment manifests, branch-protection required checks, and release artifacts therefore remain unverified.
